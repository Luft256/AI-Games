# ゲーム制作とプレイ評価

数を増やしながら、遊んだときの判断・上達・再挑戦する理由を磨きます。AIによる評価は改善の材料であり、人間の楽しさを実証したものではありません。

## 制作の単位

ゲームごとに最新の `origin/dev` から `codex/game-<id>` ブランチと独立したworktreeを作り、GPT-6.1 Sol / high のサブエージェントが実装します。共通ファイルは統合担当が扱います。各ゲームのPRは `dev` 宛てに作り、検証と改善後にマージします。`main` への反映には、その時点の `dev` に対するユーザーの公開承認が必要です。

1プレイには自然なゴールや終了条件を置き、短い休憩で遊べる長さにします。共通セッション制限も接続し、停止・バックグラウンドを含めて30分以内に終了させます。途中のパズルをクリア記録として保存しません。

## 独立したプレイ評価

実装担当以外がブラウザで実際に操作します。初回の理解、最初の失敗、再挑戦、成功または自然終了を確認し、操作した手順と観察を残します。プレイできなかった範囲は未評価と書きます。

| 観点 | 評価する内容 |
| --- | --- |
| 理解 | 何を目指し、何を操作するかが初回で分かる |
| 選択 | 判断によって結果が変わり、単なる待機や偶然だけにならない |
| 上達 | 失敗から学べる。予告・ヒント・練習で改善できる |
| 手応え | 成功・失敗の理由が見え、入力の反応が心地よい |
| 再挑戦 | 別の戦略、目標、短い再開など、もう一度遊ぶ理由がある |

各観点は1〜5点。1は重大な欠点、3は遊べるが改善余地が大きい、5はプレイの具体的な証拠がある強みです。合計点だけを合格判定にしません。入力できない、終了しない、攻略不能、理不尽な失敗、スマホで重要情報が読めない等は先に修正します。

## 評価から改善へ

指摘には「再現操作 → 観察 → 遊びへの影響 → 改善案」を付けます。実装担当に返して修正し、同じ操作を再確認します。採用しない案には理由を記録します。PC・幅320px・キーボード・タッチ、自然終了・再開・30分上限・保存禁止環境も確認します。

評価記録は `docs/playtests/` に保存します。報告には評価時のブランチまたはコミット、実操作の範囲、未評価の範囲、修正前後を含めます。

## 次のゲームを選ぶ

同じルールの見た目違いを増やすより、既存の不足を補う遊びを選びます。運と判断、照準と物理、経路計画と予告、短い連鎖などを組み合わせ、小さく完成する範囲で作ります。新作の追加と既存作の改善を交互に行います。評価で重大な問題が見つかった場合は、追加本数より修正を優先します。

## 未解決の指摘

定期スケジュールは設定しません。マージ済みのゲーム・ページに残る修正点と改善案は、対象PR・観察・期待する動作・確認方法を付けてGitHub Issueに記録します。開発中で未マージの新作はIssueにせず、その作業ブランチで修正・再確認します。修正済みの指摘を未解決Issueとして重複登録しません。
